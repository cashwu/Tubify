# rename-download-title 計畫

> 日期：2026-11-07　任務文件：[../task/2026-11-07-rename-download-title.md](../task/2026-11-07-rename-download-title.md)　規格：[download-ui-workflows](../specs/download-ui-workflows.md)（T5 補上）

## 1. 要解決的問題與成功條件

YouTube 原始標題常常很長，或帶有「｜大耳朵 TV」這類尾綴，下載後的檔名不是使用者要的。現在只能等下載完成後再去 Finder 手動改名。

**成功條件**：在下載清單上雙擊 title（或用右鍵選單的「重新命名…」）會跳出輸入視窗，裡面帶入目前的名稱。確認後，清單顯示新名稱，磁碟上的影片檔與字幕檔最後也會使用這個名稱。任何狀態都能改名（播放清單佔位項目除外），而且不會中斷進行中的下載。互動方式參考 Downie 的「輸入新的檔案名稱」視窗。

### 現況（看程式碼推論）

- 清單顯示的是 `DownloadTask.title`（`Tubify/Views/DownloadItemView.swift:90`），只用於顯示、通知與 log。
- 檔名由 yt-dlp 的 `%(title)s` 決定，只有在指令模板沒有 `-o`／`--output` 時，才會補上 `<downloadFolder>/%(title)s.%(ext)s`（`Tubify/Services/YTDLPService.swift:917-920`）。只改 `task.title` 不會改到檔名。
- 下載完成後，最終路徑來自 `--print after_move:FINAL_PATH:%(filepath)s`；`__real_download` 為 False，代表 yt-dlp 沿用了既有的同名檔（`YTDLPService.swift:933-938`、`:1016-1036`）。
- 完成流程（`Tubify/ViewModels/DownloadManager.swift:951-1056`）會依序進行首播長度檢查、設定 `task.outputPath`、送出完成通知與 Whispify callback（`filePath: outputPath`），最後依設定自動移除。
- 有幾處程式用 `task.title` 的佔位字串判斷狀態：`"載入播放清單中..."`、`"載入中..."`（`DownloadManager.swift:208,222`），以及 `"無法獲取標題"`（`:1013`）。
- 元資料抓取成功時會寫入 `task.title = videoInfo.title`（`DownloadManager.swift:457`），失敗時則改用網頁標題或 `"無法獲取標題"`（`:560-579`）。
- 字幕以 `--sub-format srt` 下載，與影片放在同一個資料夾（`YTDLPService.swift:953-954`）。檔名格式應該是 `<主檔名>.<語言>.srt`（尚未驗證，見 §5）。
- 「在 Finder 中顯示」使用的是 `task.outputPath`（`DownloadManager.swift:1269-1272`）。
- 可存取性規格要求每個操作都能用鍵盤觸發，並且有可存取性標籤（`docs/specs/download-ui-workflows.md` 的「Accessible and consistent controls」）。

## 2. 不做清單

| 項目 | 原因 |
| ---- | ---- |
| 在清單內直接編輯（inline） | 使用者要的是跳出式輸入視窗。 |
| 設定頁加入檔名模板，或修改 yt-dlp 的 `-o` 模板 | 逐筆改名就能解決問題；全域模板是另一個需求。 |
| 批次改名 | 使用者沒有要求。 |
| 「還原成原始標題」按鈕 | 想還原時再改一次就好。 |
| 修改副檔名 | 輸入框只放主檔名，副檔名由 yt-dlp 決定，維持不變。 |
| 改名後通知 Whispify 新路徑 | 使用者已決定照樣改名，不另外補發 callback；已送出的路徑可能失效，屬於已接受的風險。 |
| 預先檢查檔名長度、開頭的 `.` 等檔案系統限制 | 很少見；失敗時依 R10／R11 處理即可。 |
| 播放清單展開前的佔位項目可以改名 | 展開後就會被個別影片任務取代，改了沒有意義。 |
| 改名時中斷或重新啟動進行中的 yt-dlp 程序 | 會讓進度歸零，也會影響 `.part` 續傳；名稱改為在完成時套用。 |
| 搬移 `.part` 等中間檔 | 中間檔由 yt-dlp 管理，改名只處理最終檔案。 |

## 3. 要做的內容

| 內容 | 對應的問題 |
| ---- | ---- |
| 使用者自訂名稱：與元資料標題分開保存並持久化，清單優先顯示 | 讓改名在元資料載入、重試、重啟後都保留（R5、R6） |
| 改名視窗：雙擊 title 或右鍵選單「重新命名…」 | 改名入口（R1–R3） |
| 下載完成時，把最終檔案與字幕改成自訂名稱 | 檔名才是使用者真正要的結果（R7–R10） |
| 已完成的任務：直接在磁碟上改名 | 下載完才想改名的情境（R11） |
| 規格同步 | repo 慣例：規格是實作與測試的依據 |

### 行為規則

- **R1 入口**：雙擊清單項目的 title 文字、在右鍵選單選「重新命名…」，或用 Tab 把鍵盤焦點移到 title 後按 Enter，都會開啟同一個改名視窗。title 取得焦點時要顯示焦點框，並提供可存取性標籤。播放清單的佔位項目（尚未展開）不會開啟視窗，右鍵選單也沒有這個選項。
- **R2 視窗**：說明文字是「輸入新的檔案名稱：」，輸入框帶入目前清單顯示的名稱，按鈕為「取消」與「重新命名」。Enter 等於「重新命名」，Esc 等於「取消」。
- **R3 輸入驗證**：去掉前後空白後如果是空字串，「重新命名」不能按。去掉空白後如果和目前顯示的名稱相同，就視為沒有變更。
- **R4 檔名轉換**：清單照使用者輸入的內容顯示（去掉前後空白）。寫入檔名時，`/` 換成 `⧸`、`:` 換成 `：`，和 yt-dlp 的預設替換一致。
- **R5 不被覆寫**：任務有自訂名稱後，元資料抓取（包含重新載入、網頁標題退路，以及完成時用檔名補標題的邏輯）都不能覆蓋清單顯示的名稱。既有用佔位標題判斷狀態的復原邏輯（`DownloadManager.swift:208,222`）不能因為改名而失效。
- **R6 持久化**：自訂名稱隨任務一起存檔，重啟 App 後仍然保留並生效。舊版存檔沒有這個欄位時，要能正常讀取。
- **R7 套用時機**：任務尚未完成時（等待中、獲取資訊中、等待選擇、下載中、已暫停、失敗、取消、首播排程或串流中、直播處理中），改名只會更新顯示名稱與自訂名稱，不會中斷或重新啟動下載。yt-dlp 仍然用原本的方式產生檔案。等下載成功、通過首播長度檢查後，才把最終檔案改名，然後送出完成通知、callback，並設定 `outputPath`。
- **R8 字幕跟著改名**：只有屬於這個任務的字幕會跟著影片改名（或複製），保留語言與副檔名部分，例如 `舊.zh-Hant.srt` → `新.zh-Hant.srt`。字幕是否屬於這個任務，判斷依據是任務的字幕選擇（`subtitleSelection` 的上傳字幕與自動字幕語言）：與影片在同一資料夾，且檔名為 `<影片主檔名>.<所選語言>.srt` 的檔案。沒有選字幕的任務不動任何字幕檔，即使旁邊有同主檔名的字幕。下載完成時與已完成後改名都用這條規則。
- **R9 同名衝突**：影片與所有要處理的字幕使用同一個主檔名。只要其中任何一個目標檔名已被其他檔案佔用，就依序嘗試 `新 (1)`、`新 (2)`……，直到影片與字幕的目標檔名全部可用為止。清單仍然顯示使用者輸入的名稱。不會覆蓋任何既有檔案。
- **R10 沿用既有檔**：如果 yt-dlp 這次沿用了既有的同名檔（`__real_download` 為 False），而任務有自訂名稱，就複製出新名稱的檔案，原檔不動。字幕依 R8 的規則同樣用複製的。任務要持久化記錄 `outputPath` 指向的檔案是否屬於這個任務：實際下載產生的、或複製出來的屬於本任務；沿用的不屬於。
- **R11 失敗退路**：
  - 下載完成時改名（或複製）失敗：任務仍然標記為完成，`outputPath` 指向 yt-dlp 的原始檔案，清單改為顯示實際檔名（主檔名），失敗原因寫進 log。完成通知與 callback 使用原始路徑。
  - 已完成任務改名失敗（找不到檔案、沒有權限等）：顯示錯誤提示並說明原因，名稱、檔案與 `outputPath` 都維持原狀。
- **R12 已完成任務**：確認後立即處理磁碟上的影片檔與 R8 所指的字幕檔，同樣適用 R4、R9，並更新 `outputPath`。檔案屬於本任務時直接改名；依 R10 記錄為沿用的檔案則複製成新名稱、原檔不動，複製出的檔案從此屬於本任務。App 更新前完成、沒有來源記錄的舊任務，視為屬於本任務（直接改名）。之後「在 Finder 中顯示」會指向新檔案。屬於本任務的檔案只改大小寫（例如 `abc` → `ABC`）也要能改名成功，不能被當成和自己衝突。沿用檔需要保留原檔，所以只改大小寫時依 R9 編號（例如 `ABC (1).mp4`）。不會重新送出 callback 或通知。

## 5. 待驗證

| 假設 | 驗證方式 | 推翻時的處理 |
| ---- | ---- | ---- |
| 字幕檔名為 `<主檔名>.<所選語言 key>.srt`，與影片放在同一資料夾（上傳字幕與自動字幕皆然） | T3 開工前，實際下載一支帶上傳字幕與自動字幕的影片並確認檔名 | 依實際的命名方式調整 R8 的比對規則，歸屬原則（只處理所選語言）不變 |
| yt-dlp 預設會把 `/` 替換成 `⧸`、`:` 替換成 `：` | T1 開工前，用含這兩個字元的標題實際下載一次 | 若替換字元不同，R4 跟著 yt-dlp 的實際行為調整，並同步更新 E7 |
| `__real_download` 為 False 時，`FINAL_PATH` 仍然指向既有檔（E5） | 在已存在同名檔的情況下實際下載一次 | 若沒有 `FINAL_PATH`，就改用既有的 outputPath 推斷邏輯取得路徑；R10 不變 |
| 使用者自訂指令模板帶 `-o` 時，檔案可能位於子資料夾 | 看程式碼推論 | 改名一律在原檔案所在的資料夾內進行，不搬移資料夾 |

## 6. 實作順序與依賴

T1（模型與名稱規則）→ T2（改名視窗）與 T3（下載完成時套用）可以並行 → T4（已完成任務改名，重用 T3 的改名邏輯）→ T5（規格同步）。細節見[任務文件](../task/2026-11-07-rename-download-title.md)。目前所有 task 都尚未實作。

## 決策紀錄

- 使用者決定：改名同時影響顯示名稱與檔名；所有狀態都能改名；同名時自動加編號；yt-dlp 沿用既有檔時複製一份，已完成任務改名時沿用檔也複製，沒有來源記錄的舊任務視為自己的；Whispify 任務照樣允許改名；加入右鍵選單「重新命名…」；鍵盤以 Tab 聚焦 title 後按 Enter 觸發；確認 R11（下載完成時改名失敗的處理方式）。
- 由規劃者決定（使用者已確認計畫）：R2 的文案、R3、R4 的替換字元、R11、R1 排除播放清單佔位項目、R9 清單顯示使用者輸入的名稱；依外部 review 補上 R8 的字幕歸屬規則（只處理所選語言），以及 R9 的影片與字幕一起判斷衝突。
